This is the best audit cycle the project has had. **27 of the 29 findings from May 14 are verified fixed** — including both High-severity items (prompt injection in the NL tool loop, MemoryMonitor race) that had persisted for two cycles — plus the process recommendations (CI workflow added, pytest-cov and AI deps in dev extras, version drift now guarded by `tests/test_version.py`). This run found **0 Critical, 1 High, 5 Medium, 9 Low**. The High is a real behavioural gap in the new auto-heal feature: the `_unhealthy_alerted` dedup set means a container that is restarted and *stays* unhealthy never re-enters `heal()` — the documented "max_restarts within window" storm guard and the give-up escalation alert are only reachable for flapping containers, and a failed restart is reported as a successful attempt. Five subagent claims were struck during verification as misreads or severity inflation (details inline) — they are recorded so future cycles don't re-add them.

## High Priority Issues

### H1-2026-06 — Auto-heal retries and give-up escalation are unreachable for containers that stay unhealthy

**Severity:** High | **Category:** Bug — New Feature Behaviour
**Files:** `src/monitors/docker_events.py:558-570`, `src/services/auto_healer.py:45-64`
**Status:** New (feature shipped in v0.12/v0.14)

The unhealthy handler dedups **before** the auto-heal branch:

```python
# docker_events.py:558-561
if container_name in self._unhealthy_alerted:
    return
self._unhealthy_alerted.add(container_name)
...
if self._auto_healer is not None and self._auto_healer.is_enabled(container_name):
    await self._auto_healer.heal(container_name)
    return
```

`_unhealthy_alerted` is only cleared on a `healthy` event (line 423) or reconnect (line 317). So for a container that auto-heal restarts and that comes back **still unhealthy** (the common failure case — bad config, broken dependency), the next `health_status: unhealthy` event hits the dedup guard at line 559 and returns. `heal()` is never called again:

- The documented storm guard ("after `max_restarts` within `window_minutes` the healer gives up and sends a single escalation") is only reachable for **flapping** containers that pass through `healthy` between failures. A persistently-broken container gets exactly **one** restart attempt and then silence.
- Compounding it, `heal()` ignores the result of `controller.restart()` — which returns `"❌ Failed to restart …"` on failure (`container_control.py:36-39`) — and unconditionally sends the "attempt N/M" alert. A failed restart is reported to the user as if the heal attempt happened.

**User impact:** Someone opts a container into auto-heal, sees "🔄 Auto-heal attempt 1/3", and reasonably assumes the bot is on it. The container can then sit unhealthy indefinitely with no further alert — the give-up escalation never fires.

**Fix:**
1. In the auto-heal branch, allow re-entry: after `await self._auto_healer.heal(...)`, `self._unhealthy_alerted.discard(container_name)` so the post-restart unhealthy event re-enters `heal()` (the storm guard then provides the loop bound it was designed for). Keep the flag set on the *give-up* path so escalation isn't repeated — e.g. have `heal()` return whether it has given up, and only discard when it hasn't.
2. In `heal()`, check the restart result: `result = await self._controller.restart(...)`; if `result.startswith("❌")`, send a failure-flavoured alert (or fall through to the normal `send_health_alert`) instead of the success-implying attempt alert.
3. Add a test: unhealthy → heal → unhealthy (no healthy in between) must produce a second heal attempt, and the (max_restarts+1)-th must produce the gave-up escalation.

## Medium Priority Issues

### M1-2026-06 — `fh_tog`/`fh_save` write unvalidated callback data into config.yaml

**Severity:** Medium | **Category:** Input Validation
**Files:** `src/bot/manage_command.py:662-670`, `src/config.py:395-403`

The auto-heal picker toggle accepts any non-empty string from callback data and stores it; Save persists it to config.yaml:

```python
# manage_command.py — no validate_container_name(), unlike every other handler
parts = data.split(":", 1)
if len(parts) < 2 or not parts[1]:
    await callback.answer("Invalid selection")
    return
container = parts[1]
selection_state.toggle(user_id, container)
```

```python
# config.py:403 — no per-name validation
self.containers = list(containers)
```

A modified Telegram client (still an *allowed* user, so impact is bounded) can persist arbitrary strings into `auto_heal.containers`. `yaml.dump` keeps it structurally safe and `AutoHealer.is_enabled()` only does membership checks, so this is config pollution rather than code execution — but it's the **only** callback family that skips `validate_container_name()` (used at `alert_callbacks.py:60,125,227,…`), and junk entries silently flip `enabled: true`.

**Fix:** Validate in the toggle handler (reject names failing `validate_container_name`, or better: reject names not in `_heal_candidates()`), and defensively filter in `set_containers()`.

### M2-2026-06 — Diagnostic context gathering crashes on Docker hiccups after "Analyzing…"

**Severity:** Medium | **Category:** Error Handling
**File:** `src/services/diagnostic.py:124-131`

Only `docker.errors.NotFound` is handled, and only around `containers.get`:

```python
try:
    container = await asyncio.to_thread(self._docker.containers.get, container_name)
except docker.errors.NotFound:
    return None

# Get logs — UNGUARDED
log_bytes = await asyncio.to_thread(container.logs, tail=lines, timestamps=False)
```

A `docker.errors.APIError` from `containers.get`, or any exception from `container.logs` (daemon restarting, socket timeout), propagates out of `gather_context()` into the callback handler after the user has already been shown "Analyzing…" — they get silence, the error lands only in the bot log. The image fetch below it (lines 151-159) *is* defensively wrapped, so the gap is inconsistent.

**Fix:** Broaden the `containers.get` except to `docker.errors.DockerException` → return None; wrap the `container.logs` call and degrade to `logs = "(logs unavailable)"` so a partial diagnosis still reaches the user.

### M3-2026-06 — Unraid API error paths still leak unredacted response bodies (carryover L8, partially fixed)

**Severity:** Medium | **Category:** Security — Data Exposure
**File:** `src/unraid/client.py:195-209`

`connect()` now truncates to 200 chars and redacts the API key — but the two error paths in `_execute_query()` don't:

```python
if response.status != 200:
    text = await response.text()
    raise UnraidConnectionError(f"GraphQL request failed: {response.status} - {text}")   # full body, no redaction
...
except json.JSONDecodeError as e:
    text = await response.text()
    raise UnraidConnectionError(f"Invalid JSON response: {e}. Response: {text[:200]}")   # truncated, no redaction
```

These exception messages are logged by callers on every poll failure. The realistic risk is an error page echoing request details (the key travels in `x-api-key`), not an attacker-controlled server — hence Medium, not the Critical one subagent suggested. It's a two-line consistency fix.

**Fix:** Extract the truncate+redact treatment from `connect()` into a small `_safe_body(text)` helper and use it in all three places.

### M4-2026-06 — Image-update dedup is in-memory; every bot restart re-announces pending updates

**Severity:** Medium | **Category:** Bug — Dedup Durability
**File:** `src/monitors/image_update_monitor.py:45,97-99`

`self._notified: dict[str, str]` (container → announced remote digest) is never persisted. The bot now restarts *itself* routinely — `/restart`, setup wizard, and the new `/manage → Features` image-updates toggle all call `restart_bot()` (`main.py:85,125`, `startup.py:475`). After each restart, the first poll re-announces every update the user already saw and chose not to pull. With restart-to-apply now a normal UX flow, duplicate digests will be a recurring annoyance rather than an edge case.

**Fix:** Persist `_notified` to `data/announced_updates.json` using the `version_store.py` atomic pattern; load at init. Prune entries whose container no longer exists during `check_once()` (also closes the trivial unbounded-growth residue for removed containers).

### M5-2026-06 — Callback parse/validate/lookup boilerplate ×10 in alert_callbacks.py (carryover M9, partially fixed)

**Severity:** Medium | **Category:** Maintainability — DRY
**File:** `src/bot/alert_callbacks.py` (935 lines)

The duration formatting and threshold constants were extracted last cycle (good), but the dominant pattern remains. Ten-plus handlers repeat ~15 lines of: null-check → `split(":", 1)` / `rsplit(":", 1)` → length check → `validate_container_name()` → `state.find_by_name()` → error-answer. Verified occurrences: lines 46-71, 106-139, 219-238, 303-319, 361-371, 421-431, 465-475, 594-614, 674-695, 734-741.

**Fix:** Two helpers cover all sites:
- `parse_container_callback(callback, state) -> str | None` — answers the error itself, returns resolved name or None (simple `prefix:name` cases).
- `parse_valued_callback(callback, state) -> tuple[str, int] | None` — the `prefix:name:value` rsplit variant.

Each call site shrinks to ~3 lines; the file drops well under 800 lines and every new alert button gets validation for free (which would also have prevented M1-2026-06).

## Low Priority Issues

### L1-2026-06 — AutoHealer storm-guard window uses wall clock
**File:** `src/services/auto_healer.py:46`
`datetime.now()` for the sliding window; an NTP step or DST-adjacent host clock change stretches/shrinks the window. `system_monitor.py` already uses `time.monotonic()` for exactly this. Switch `_restarts` to monotonic floats.

### L2-2026-06 — Concurrent `restart_bot()` calls interleave broadcasts
**File:** `src/restart.py:50-57`
Two simultaneous triggers (e.g. /restart button + wizard finish) both run the notice loop before the first reaches `execv`; users can receive duplicate notices. Benign — `execv` replaces the process, so nothing hangs or orphans (one subagent claimed High here; struck on verification). A module-level `_in_progress` flag is a 3-line politeness fix. The no-stop_polling design itself is correct and unusually well documented.

### L3-2026-06 — Corrupted `announced_version.json` re-shows "What's new" once
**Files:** `src/utils/version_store.py:20-21`, `src/startup.py` What's-new gate
`JSONDecodeError` → None → gate treats it as never-announced. Cosmetic (one duplicate message); optionally delete the corrupt file on read failure and log a warning.

### L4-2026-06 — `_violation_last_seen` lazily initialised via `hasattr`
**File:** `src/monitors/resource_monitor.py:393-394`
`if not hasattr(self, "_violation_last_seen")` inside `_poll_cycle()` — works, but it's the only attribute in the codebase created outside `__init__`, and mypy only tolerates it via the inline annotation. Move to `__init__`. (The eviction logic itself is correct — a subagent claim that stale entries never evict was struck on verification: `last_seen` only updates for active containers, so the 600 s clock does expire.) Residue: `_violation_last_seen` keeps one float per container name ever seen — trivial, prune alongside eviction if touching this code.

### L5-2026-06 — `extract_local_digests(container: Any)`
**File:** `src/monitors/image_update_monitor.py:13`
Type as a Protocol or `"Container"` under TYPE_CHECKING; `Any` here defeats strict mypy on a public helper.

### L6-2026-06 — `_recent_count()` mutates state
**File:** `src/services/auto_healer.py:37-43`
Reassigns `_restarts[name]` and discards from `_gave_up` inside a "count" getter. Correct behaviour, misleading name — rename to `_prune_and_count()` or document the side effects.

### L7-2026-06 — `atomic_yaml_write()` doesn't set file mode
**File:** `src/config.py:56-71`
`version_store.py` sets `os.fchmod(fd, 0o644)` after `mkstemp` (which creates 0o600); the YAML helper doesn't, so a fresh config.yaml written via the helper ends up 0o600. Harmless in Docker, but inconsistent — add the same `fchmod`.

### L8-2026-06 — `telegram_format.py` missing from `.claude/structure/utils.yaml`
All other new files made it into CLAUDE.md *and* the structure YAMLs; this one is only in CLAUDE.md. Five-minute doc fix (CLAUDE.md itself mandates it).
